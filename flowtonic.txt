FLOWNETIC — PORTFOLIO INTELLIGENCE


Engineering Build Specification & Product Requirements


Product: Flownetic Portfolio Intelligence
Build priority: Working sales demonstration first
Primary audience: Private equity Operating Partners, Heads of Portfolio Operations, Heads of Value Creation, and portfolio-company leadership
Initial environment: Demo environment using fictional data
Production status: Not production-ready until the security and deployment requirements are implemented and verified


---


1. PRODUCT OBJECTIVE


Build an interactive portfolio intelligence platform that helps a private equity team monitor multiple portfolio companies, identify material performance variances, investigate potential causes, assign corrective actions, and track whether those actions produce measurable results.


The platform should answer five questions:


1. Which portfolio companies require attention?
2. Which financial or operating metrics are below plan?
3. What evidence could explain the variance?
4. What action should be taken, and who owns it?
5. Did the action produce a verified improvement?


The platform must demonstrate a complete workflow, not just display charts.


Core workflow


Import data → Validate data → Calculate KPIs → Detect exceptions → Investigate evidence → Review proposed actions → Track execution → Verify outcomes.


Scope boundary


The initial product is a portfolio-performance monitoring and decision-support prototype. It is not a complete fund-accounting system, investment due-diligence engine, autonomous financial adviser, or replacement for every system used by a PE firm.


Do not add unrelated modules until the core workflow works reliably.

Use a restrained, premium, enterprise-finance aesthetic.

- Primary palette: near-black, white and neutral greys.
- Use a muted accent colour sparingly.
- Use red, amber and green only where they communicate status or severity.
- Use a clean sans-serif font.
- Use consistent spacing, borders and alignment.
- Use restrained shadows and subtle transitions.
- Avoid oversized gradients, cartoon illustrations, excessive rounded cards and decorative animations.
- Prioritise readability and information density.


Layout


Desktop:


- Fixed or collapsible left navigation.
- Main content area with a consistent maximum width.
- KPI cards at the top of overview screens.
- Charts and tables below.
- Detail panels or drawers for investigation and editing.


Mobile:


- Responsive navigation.
- Stacked KPI cards.
- Horizontally scrollable tables when necessary.
- Forms and action controls must remain usable.


Use accessible contrast, visible focus states, semantic labels and keyboard navigation.

7. SCREEN FOUR — KPI CALCULATION ENGINE


Financial calculations must be deterministic and testable. The language model must never be responsible for calculating official KPI values.


Revenue variance percentage


Revenue variance = Revenue actual − Revenue plan.


Revenue variance percentage = (Revenue actual − Revenue plan) / Revenue plan × 100.


EBITDA variance percentage


EBITDA variance percentage = (EBITDA actual − EBITDA plan) / EBITDA plan × 100.


EBITDA margin


Actual EBITDA margin = EBITDA actual / Revenue actual × 100.


Planned EBITDA margin = EBITDA plan / Revenue plan × 100.


Margin variance = Actual EBITDA margin − Planned EBITDA margin, expressed in percentage points.


Rules


- Use decimal-safe financial calculations where appropriate.
- Handle zero denominators explicitly.
- Represent missing values as missing, not zero.
- Apply consistent currency and rounding rules.
- Retain full precision internally; round for display.
- Show the calculation definition in the methodology view.
- Unit-test every formula.


Initial exception thresholds


For the prototype, use configurable example thresholds:


- High-priority exception: EBITDA variance at or below −10%.
- Optional revenue exception: revenue variance at or below −5%.
- Warning status: a less severe configurable deviation.
- On-track status: no configured threshold breached.


These thresholds are demo assumptions, not universal PE standards.


Use a central rules configuration. Do not hardcode thresholds in multiple components.


The same input data and rules must always produce the same calculated metrics and exception decisions.

9. SCREEN SIX — AI-ASSISTED INVESTIGATION


Purpose: Help an analyst organise evidence and investigate why a company is underperforming.


Investigation input


The AI may receive:


- Relevant company KPIs.
- Variance calculations.
- Available historical observations.
- User-provided notes.
- Relevant uploaded documents, if document processing has been implemented.
- Source and data-freshness metadata.


Only provide data the current user is authorised to access.


Required output structure


Return a structured investigation containing:


1. Executive summary.
2. Confirmed observations.
3. Potential explanations.
4. Evidence supporting each explanation.
5. Evidence that is missing.
6. Questions for the company management team.
7. Recommended next investigative steps.
8. Suggested actions for human review.
9. Confidence or evidence-strength assessment.
10. Data limitations.


Mandatory distinction


Separate confirmed facts from hypotheses.


For example:


Confirmed observation:
“Revenue was 3.6% below plan in the selected reporting period.”


Potential explanation:
“Lower sales volume could contribute to the variance, but sales-volume data has not been supplied.”


The system must not claim that customer churn, pricing, labour costs, supply-chain problems or any other factor caused a variance unless the available evidence supports that conclusion.


User controls


Provide buttons to:


- Generate investigation.
- Regenerate analysis.
- Add analyst notes.
- Edit the investigation.
- Save investigation.
- Create a proposed action.
- Mark the investigation reviewed.


Require a human to review and approve important recommendations.


Technical requirements


- Use a structured response schema.
- Validate the model response before rendering or saving.
- Handle timeouts and API failures.
- Provide loading, error and retry states.
- Never expose a secret API key in browser code.
- Do not send confidential client data to an external AI service without the client's approval and appropriate privacy/security controls.
- Log relevant investigation metadata without unnecessarily logging sensitive financial content.


If no model API is configured, show a clearly labelled mock investigation. Never pretend a mock response was generated by a live AI model.

Purpose: Turn investigation findings into accountable work.


Action fields


- Action ID.
- Company.

- Action title.
- Description.
- Priority.
- Assigned owner or role.
- Created date.
- Due date.
- Status.
- Completion notes.
- Evidence attachment or reference, if implemented.
- Verification status.


Status workflow


Proposed → Approved → In progress → Completed → Outcome verification → Verified or Reopened.

Required interactions


- Create an action from an investigation.
- Create an action manually.
- Edit action details.
- Assign or reassign an owner.
- Change priority and due date.
- Update status.
- Add progress notes.
- Filter overdue and high-priority actions.
- Open the related company and exception.
- Record completion evidence.
- Reopen an action when verification fails.


All changes must persist after refresh. For the prototype, local persistence is acceptable only if clearly scoped to a single-user demo. Prefer a small database if the engineer can implement it reliably.


11. SCREEN EIGHT — IMPACT TRACKING


Purpose: Show whether actions were followed by measurable changes.


Impact record


Each record must include:


- Related company.
- Related action.
- Metric.
- Baseline value.
- Baseline period.
- Target value.
- Target period.
- Observed value.
- Observation period.
- Measurement source.
- Verification status.
- Reviewer.
- Notes.


Rules


- Clearly distinguish targets, estimates and observed results.
- Do not label projected savings as realised savings.
- Do not attribute every improvement to an action without evidence.
- Show missing or unverified data honestly.
- Permit the outcome to be marked “not yet measurable.”
- Retain a record of changes to the measurement.


Example


A proposed action may target an improvement in EBITDA margin. The dashboard should show the baseline, the target, the latest observed margin and whether the result has been verified.


Do not claim financial benefits without an identified calculation method and supporting observations.

14. SUGGESTED TECHNICAL ARCHITECTURE


The engineer may select the stack they can support best, but the architecture must be maintainable.


Frontend


A modern React and TypeScript application, or an equivalent maintainable framework.


Use reusable components for:


- KPI cards.
- Data tables.
- Charts.
- Filters.
- Status indicators.
- Forms.
- Drawers and modals.
- Empty, loading and error states.


Backend


Use a server-side API for:


- Data import and validation.
- KPI calculations.
- Exception generation.
- Persistence.
- Investigation orchestration.
- Action management.
- Impact records.
- Authentication and authorisation when required.


Database


A relational database is appropriate for production. Use stable identifiers and relationships between companies, observations, exceptions, investigations, actions and impact records.


AI integration


Keep model-provider credentials on the server. Use schema-validated inputs and outputs, access controls and failure handling.


Charts


Use a maintained charting library. Charts must be driven by application data and update when the selected filters change.


Configuration


Keep reporting periods, thresholds, currency and other business rules configurable rather than scattering values through the code.


Environment separation


Maintain separate demo and production configurations. Demo data must not be mixed into a client's production workspace.

17. ACCEPTANCE TESTS


The demo is not complete until the following checks pass.


Calculations


- Revenue and EBITDA variance formulas return correct results.
- Margin is calculated correctly.
- Zero denominators do not cause crashes or misleading numbers.
- Missing values remain missing.
- Display rounding does not change the stored result.


Data import


- Valid CSV files import successfully.
- Invalid rows generate useful errors.
- Duplicate records are handled consistently.
- The import summary matches the actual import outcome.


Dashboard


- KPI counts match the stored records.
- Filters and search return the correct rows.
- Company detail pages show the selected company.
- Charts update when filters change.
- Empty states work.


Exceptions


- Threshold changes affect exception generation consistently.
- Each exception displays its triggering rule.
- A resolved exception retains its history.
- Invalid data does not silently create a false alert.


AI investigation


- Facts and hypotheses are separated.
- Missing evidence is disclosed.
- Invalid model output is handled safely.
- API failure produces a useful error and retry option.
- A mock investigation is clearly labelled.


Actions and impact


- Action edits persist.
- Status changes update the interface.
- Overdue actions are identified correctly.
- Impact records distinguish targets from observed results.
- Unverified results are never shown as verified.


General


- No dead buttons or broken navigation.
- No sensitive API keys in frontend bundles.
- No console errors during the standard demo workflow.
- The fictional-data notice is visible.
- The app remains usable at desktop and mobile widths.


18. PRODUCTION REQUIREMENTS — NOT OPTIONAL BEFORE REAL CLIENT DATA


The sales prototype must not be represented as ready for confidential PE financial information.


Before production use, implement and verify:


- Authentication and secure session management.
- Role-based access control.
- Workspace and tenant isolation.
- Server-side authorisation on every sensitive request.
- Encryption in transit and appropriate encryption at rest.
- Secure secrets management.
- Audit logs for data access and material changes.
- Secure file upload, validation and storage.
- Backup and recovery procedures.
- Error monitoring and operational alerts.
- Rate limiting and abuse protection.
- Data retention and deletion controls.
- Appropriate privacy, contractual and AI-provider controls.
- Integration tests and security testing.
- A documented deployment and rollback procedure.
- Clear limitations for AI-generated analysis.
- Human review of important decisions.


Integrations with accounting, ERP, CRM or portfolio-company systems must be scoped separately. Do not claim an integration exists until it has been built and tested.

FINAL DEFINITION OF DONE


A user can import fictional data, review calculated portfolio performance, investigate a real rule-triggered exception, create and manage an action, record an observed outcome, and trace the key information back to its source—all in one working application.
